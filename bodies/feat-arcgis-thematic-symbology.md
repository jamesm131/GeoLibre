## Summary

ArcGIS Pro projects (`.aprx`, `.mapx`) now keep their thematic symbology. A layer symbolised by **unique values** on one field, or by **graduated colours**, imports as a rule-based style with one rule per class: the class's label, colour, outline and order, its checkbox (an unchecked class is a switched-off rule), and the "all other values" / out-of-range class as the catch-all rule. Before this change every such layer was flattened to its default symbol's single colour, with no warning.

Supported renderer limitations produce per-layer warnings in the existing import warnings dialog, one per reason. Those notes describe a layer that did load, so they are not counted as "layers that could not be loaded". Neither is the existing map-extent note, which describes the view rather than a layer: on `main` a project whose only note was the extent said "1 layer could not be loaded". A report with only such notes now says the project is not shown exactly as in ArcGIS Pro (`countArcgisUnloadedLayers`). Point markers are still drawn as circles, but a marker of any other shape (a square, a star, a font glyph) now gets a `marker-shape` note saying so.

CIM symbology reading now has one home, `packages/map/src/cim-renderer.ts`, exported from `@geolibre/map/style-import` next to the SLD, QML and Mapbox style importers. The APRX importer uses it instead of its own `cimColor` copy, and a follow-up PR rebuilds the `.lyrx` importer merged in #3545 on it.

## How it works

Everything CIM-specific is in one pure module with no `maplibre-gl` import, `packages/map/src/cim-renderer.ts`. `@geolibre/map/style-import` re-exports its public API, which the module header documents for CIM importers:

- `translateCimRenderer(renderer: unknown): CimRendererTranslation`, the entry point for a layer's `renderer`.
- `translateCimSymbol(reference: unknown): CimRendererTranslation`, one `CIMSymbolReference` as a single-symbol style.
- `cimColor(value: unknown): CimColor | null` (`{ hex, opacity }`).
- `cimSymbolLayerEnabled(layer: unknown): boolean`.
- Types `CimRendererTranslation` (`{ translated, style, issues }`), `CimRendererIssue` (`{ code, cimType? }`), `CimRendererIssueCode` and `CimColor`.

In short:

1. **Shared CIM readers.** `cimColor` supports RGB (0–255), Gray, CMYK (0–100), HSV (hue 0–360, S/V 0–100) and LAB (D50, as CSS `lab()`), with alpha (0–100) as a 0–1 opacity; other subclasses (HSL, XYZ, Spot and so on), too few channels, or any channel that is not a finite JSON number (`null`, `""`, `true`, and also numeric strings such as `"255"`, which the old importer read and Pro never writes) return `null` rather than a guessed colour: `Number(null)` is 0, which would have read a broken colour as black. The hex string comes from `rgbToHex` in `@geolibre/core`. `cimSymbolLayerEnabled` is the one place the `enable` flag is read (see design decisions).
2. **`translateCimRenderer`** dispatches on the renderer type:
   - `CIMSimpleRenderer` → a single-symbol style.
   - `CIMUniqueValueRenderer` on exactly one field → one rule per class, groups flattened in order.
   - `CIMClassBreaksRenderer` with `classBreakType: "GraduatedColor"` → one rule per break.
   - Everything else is refused.
   It returns `{ translated, style, issues }`. Refused renderers retain any readable single or default symbol as a flat style, otherwise the importer uses GeoLibre's default style, plus one issue naming why.
3. **The thematic builder** turns classes into `VectorRule`s, the catch-all rule, and per-rule overrides where a class's outline colour, outline width, fill opacity or marker size differs from the first class.
4. **Symbol reading** turns one `CIMSymbolReference` into a flat look in one pass over its enabled symbol layers (CIM lists them top first): the first solid fill and first solid stroke are drawn, every other enabled layer is noted as dropped, effects are collected on the way, and a solid fill or stroke whose colour cannot be read is noted as unreadable rather than treated as absent. A marker reads its first drawing graphic the same way.

The APRX importer's `parseStyle` now just calls `translateCimRenderer` and turns each issue into a warning carrying the layer's import id (`layerId`, already on main). When a caller later drops the layer with `dropArcgisImportLayers`, as the browser build does for local-file layers, its symbology notes go with it. The import dialog picks the issue's own message (`toolbar.item.arcgisSymbologyIssue.<code>`).

**What is refused, and how the user is told.** Each refusal is one warning on the layer, which still loads with its single or default symbol where that can be read: another renderer type such as proportional symbols, dot density or heat map (`renderer`), unique values on several fields or on none (`multiple-fields`), an Arcade expression (`expression`, which CIM says wins even when a field is also listed), normalised breaks (`normalization`), graduated symbols (`graduated-symbols`), an exclusion clause (`exclusion`), a class symbol with no solid colour such as a picture fill with no outline (`symbol`), or no usable classes, including breaks that are not strictly ascending or a bound that is present but not a number (`no-classes`). A translated renderer can still carry notes for what it leaves out: visual variables (`visual-variables`), symbol layers it does not draw such as hatching, a cased line's casing, markers along a line, or a hatch or second graphic inside a marker (`symbol-layers`), a solid fill or outline whose colour cannot be read, such as a `CIMHSLColor` or an RGB colour with a `null` channel, which is then not drawn (`color`), geometric effects such as dashes or offsets, including those inside marker graphics, also for markers along a line that are not drawn themselves, and a point marker's own `offsetX`/`offsetY`, which a circle layer cannot draw (`effects`), outline or line transparency that differs from what the class actually draws with (`transparency`), a point marker whose shape is not a circle, which is drawn as one (`marker-shape`), and alternate symbols that ArcGIS Pro draws at other scales on the renderer, a class or a break, of which only the primary symbol is drawn (`alternate-symbols`).

## Design decisions and known limits

- **Rules, not GeoLibre's native categorised/graduated modes.** A class break is `(previous upper bound, upper bound]`, the first `[minimumBreak, upper bound]`. The native graduated `step` is lower-bound inclusive and paints values below the first stop, and empty values, in the first class, so every value that sits exactly on a break would land in the wrong class. Both native modes also always draw unclassified values in a fallback colour, while ArcGIS hides them unless "all other values" / out-of-range is on. One rule per class keeps the exact filter, label, colour and order. The tests evaluate the generated filters and paint values with MapLibre's own expression engine, including values exactly on a break, the minimum, below the minimum, above the top break, `null` and missing.
- **Unique values are matched as text.** ArcGIS stores every unique value as a string whatever the field type, so the feature value goes through `to-string` and is tested with `in` against the class's values (`3` matches `"3"`). `in` rather than `match`, because MapLibre's `match` rejects a label named like an `Object.prototype` key (`toString`, `constructor`) as a duplicate. `<Null>` matches a null or missing value and is kept apart from the text match, because `to-string(null)` is `""` and would otherwise also match an empty-text class. A stored number spelled differently from JavaScript's canonical form (`"1.0"`, `"1E+21"`, `"-0"`) is also compared numerically, against numeric feature values only, so text fields still need the exact text. A numeric value in hand-written CIM is read as its text. Booleans follow the same rule: feature values `true` and `false` match stored `"true"` and `"false"`. In hand-written CIM, a boolean value is read as its text and a JSON `null` as `<Null>`; any other value refuses the renderer (`no-classes`) rather than being dropped. Date fields are a known gap, also stated in the user guide: ArcGIS's stored date text will rarely equal the feature's value. There is no warning, because a field's type is in the file only for some data connections (a query layer's `queryFields`).
- **Multi-field unique values are refused, not approximated.** ArcGIS joins the fields with a field delimiter and matches the combination; reproducing that needs the delimiter and type handling per field, so the layer gets a `multiple-fields` warning and its default symbol. A unique value renderer that lists no field at all gets the same code, and the warning text says unique values are supported only on exactly one field, not on several fields or none, so it is true in both cases. A separate code would only split one message into two.
- **Class breaks classify numbers only.** A feature value that is not a number (including `null`, which `to-number` would turn into 0) is left out of every class, as ArcGIS leaves nulls out; it draws only with the out-of-range symbol.
- **Defaults follow CIM serialisation.** CIM JSON leaves out a property at its default, so an absent `upperBound` or `minimumBreak` reads as 0, An absent stroke `width` or marker `size` also reads as 0, though not by that rule: Pro always writes both (all 1,747 solid strokes and 624 markers in 113 Pro `.lyrx` exports do, 146 strokes with an explicit `0`), so the absent case comes only from other tools, and 0 stops such a class inheriting the first class's outline or GeoLibre's 2px default. A size-0 marker also drops its outline, which a circle layer would otherwise draw as a ring. Pro writes `visible: true` on every shown class, so where any class carries `visible`, a class without it was saved unchecked; files from before the property existed carry it on no class, and every class shows. Known limit: if every class was saved unchecked, the file looks the same as an old one and every class shows; there is no renderer-level flag to tell the two apart, and a layer with every class hidden draws nothing in ArcGIS Pro either way, so this case is rare. `isDefaultSymbolVisible` (Pro 3.4+) is honoured only when it is explicitly `false`, because earlier files leave it out while drawing the default.
- **Symbol-layer `enable`: only an explicit `false` switches a layer off.** The seven checked Pro exports write `enable` on every symbol layer, `true` or `false` (every symbol layer in the seven public `.lyrx` files below carries the flag, and Esri Japan's Pro 2.6 zoning layer writes `"enable" : false` on its outlines). So for those files the choice does not matter; for CIM from other tools, which sometimes omits the flag on layers meant to draw, absent means enabled. This is in `cimSymbolLayerEnabled` so every reader treats it the same way.
- **Unchecked class while "all other values" draws.** A disabled GeoLibre rule lets its features fall through to the catch-all, but ArcGIS hides an unchecked class's features even then. In that case the default symbol becomes an explicit "none of the classes" rule and the catch-all is switched off, which keeps both behaviours.
- **Draw order.** Rules are one map layer evaluated first match first, so features draw in data order whatever their class, as they do in ArcGIS Pro unless symbol level drawing is turned on (not reproduced). Pro-generated classes never share a value or range, so rule order affects only the legend (if hand-written CIM repeats a value across classes, the first enabled matching rule wins); `showInAscendingOrder: false` reverses it to match ArcGIS's legend.
- **Hatch, picture and gradient fills.** A polygon whose only fill cannot be drawn flat keeps its outline (hollow) and gets a `symbol-layers` note; see the next point for when nothing visible is left.
- **Nothing visible left means refused, not imported invisible.** For polygons, lines and markers alike, when a layer that was left out (dropped or unreadable) is all that would show, such as a hatch over a clear background, a transparent or zero-width top stroke over a dropped casing, a clear or size-0 marker over a second opaque one, or a clear fill under an unreadable outline, the symbol is refused (`symbol`). A symbol made only of supported layers that is itself transparent (an invisible outline-only class, say) is carried as it is, because ArcGIS Pro draws nothing for it either. Before this change the importer kept such a layer's outline colour, so this keeps that behaviour rather than falling back to GeoLibre's default style.
- **Per-class stroke transparency.** A rule can override outline colour and width but not outline opacity, so every class draws its outline (or line) at the layer's stroke opacity, which comes from the first class (or GeoLibre's default of fully opaque when the first class has no outline). Any class whose outline asks for something else gets the layer a `transparency` note. Fill and marker transparency are carried per class.
- **Geometric effects are reported, not drawn.** Dashes, offsets and other `CIMGeometricEffect*` entries on a symbol or its enabled layers change the drawn shape; a rule cannot hold a dash pattern per class, so lines draw solid and in place and the layer gets an `effects` note naming the first effect. Two of the seven real files below (GeMS contacts and faults, and a watershed flow-path layer) use dashes.
- **Markers are drawn as circles, with a warning when that changes the shape.** A marker becomes a circle in the marker's colour and size. A marker whose shape is not a circle gets a `marker-shape` note naming its type: a character marker (font glyph), or a vector marker whose drawing graphic is anything but a circle as ArcGIS Pro writes one, a single curve ring with one arc back to its start point. A square written as `rings`, a rounded shape with more segments, or an ellipse (an elliptic arc whose axis ratio is not 1) all count as other shapes. So does a shape that cannot be confirmed: a graphic with no geometry, or a vector marker with no graphic that draws (drawn by the marker's own colour alone). Only a marker whose every drawing graphic is a circle stays silent. Pro's own circle marker, as in the Fire Stations export below, gets no note, so a plain point layer is not flagged. The circle takes its fill and outline from the marker's first graphic that draws anything; a second graphic (`CIMMarkerGraphic`) or a hatch inside the drawn graphic is reported as `symbol-layers`. Marker approximation requires a readable fill in the selected graphic (or the marker's own colour); outline-only graphics fall back with a `symbol` warning rather than drawing an empty ring.
- **Marker outlines scale as ArcGIS Pro draws them.** A vector marker with `scaleSymbolsProportionally` gives its graphic's stroke widths at the size of its `frame`, so the outline is scaled by the marker size over the frame height (a 1pt outline in a 10pt frame is 2pt on a 20pt marker). Without that flag, or without a readable frame, the width is used as written.
- **Unreadable colours are reported, not replaced.** A solid fill or outline whose colour `cimColor` cannot read is left undrawn and reported (`color`): an unreadable fill behind a readable outline draws hollow, an unreadable outline draws no outline. Drawing it in an invented colour would pass for the real map. When nothing visible is left, the symbol is refused (`symbol`), as described above.
- **No coloured edge on a class without an outline.** GeoLibre's polygon fill draws a 1px hairline in the stroke colour even at stroke width 0 (QGIS draws a width-0 outline as a 1px pen too), so a class without an outline, or with a fully transparent one, gets width 0 and its own fill colour as its outline colour, per rule where classes differ. The hairline then matches the edge MapLibre draws for any fill. GeoLibre's general meaning of width 0 is unchanged. Exported to QML, that width-0 outline becomes QGIS's 1px pen in the fill colour, but at the stroke opacity rather than the fill's, so a translucent fill gets an opaque edge (true of every width-0 export, not only imported ones).
- **QML export of imported classes is not supported yet.** The class filters use `in`, `to-string`, `to-number` and `typeof` so values compare as ArcGIS does; the QML exporter cannot translate those expressions, so it skips each class rule with a warning and keeps only the catch-all rule. When no rule exports and the catch-all is off (class breaks without a default), `buildQml` now exports a single symbol, as it already did for categorised and graduated styles, rather than a QML that draws nothing, with a warning that the single symbol draws every feature (QGIS cannot express the class filters, so neither output matches the map). The fallback applies only when a skipped rule is one the map draws (it and its ancestors switched on); when every skipped rule is switched off, or the only rule is a switched-off catch-all, the export keeps the empty tree, which draws nothing, as on the map. The map, legend and `.geolibre` project files are unaffected.
- **Why `cim-renderer.ts`, not `arcgis-*`.** The `no-cross-engine-imports` lint rule treats `arcgis-*` files in `packages/map/src` as code for the ArcGIS map engine. This module reads a file format any engine can use, so it has a neutral name.
- **Why `@geolibre/map/style-import`.** Every other style importer (SLD, QML, Mapbox, and #3545's `.lyrx`) lives there, the entry point stays free of `maplibre-gl` so `node --test` can load it, and the desktop QGIS importer already imports from it. Nothing is added to `@geolibre/core`'s root export.
- **Units.** CIM widths and marker sizes are points; GeoLibre's are CSS pixels (×96/72). A marker's CIM size is its height, so the circle radius is half of it. Values are rounded to 4 decimal places so `0.75 pt` is written as `1`, not `0.9999999999999999`.
- **Generated labels.** Pro always writes class labels, so these are rarely used; when a break has none, the label is `lower – upper` with bounds rounded to 12 significant digits (`0.3`, not `0.30000000000000004`).
- **Only the first symbol layer type dropped is named.** One `symbol-layers` note per layer names the first undrawn layer type found; one note per reason keeps the dialog readable for layers with many classes.
- **Translations.** New strings are only in `en.json`; per `docs/i18n.md`, other catalogs fall back to English and the catalog test reports missing keys rather than failing.
