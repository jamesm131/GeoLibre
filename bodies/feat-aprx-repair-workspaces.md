## Summary

An ArcGIS Pro project records each layer's data folder as it was on the computer that saved it, usually a Windows drive (`C:\GIS\Data`) or a network share (`\\server\gis\Data`). When the project is opened anywhere else, none of those folder-backed layers load. With this change, the ArcGIS import report in GeoLibre Desktop lists each saved folder whose layers did not load. Each entry shows the names of the layers that use that folder and has a **Locate folder…** button. When the user picks the folder's new location, those layers load from it, in their saved group, under their saved names and in their saved drawing position. Their import warnings are then removed. Layers that still cannot be loaded stay listed, so the user can try another folder.

## How it works

- `arcgis-project-import.ts`: the importer keeps `repair.folderSources`, the `{ workspace, file }` of every folder-backed feature layer (shapefile, delimited text or another single-file vector format in a folder workspace). `workspace` is kept exactly as the project stored it. `file` is normalised: `/` separators, `.shp` added as before, `.` segments dropped. `folderSources` is a `Map` because layer ids come from layer names, and `constructor` or `__proto__` are valid names. A layer whose saved location is a network share is still never read and still gets its `network-path` warning. Its record is now kept in `repair.unresolvedLayers`, with the layer id on its warning. Its id is in the foundation's `layerOrder`, and `pruneArcgisImportGroups` keeps its group.
- `arcgis-workspace-repair.ts` (new):
  - `loadArcgisFolderLayers` reads the folder-backed layers before the project loads. Reads run in parallel, one per resolved path. A missing or unreadable file is set aside with a new `data-not-found` warning ("not found, or could not be read"). Before, its record was loaded, and the reopen restore then dropped it.
  - `arcgisRepairGroups` groups the waiting layers by workspace identity, top first as ArcGIS Pro lists them.
  - `readLocatedArcgisLayers` reads one workspace's files from the picked folder.
  - `commitLocatedArcgisLayers` adds them (see "Layer order" below).
- `restore-local-layers.ts`: the read-and-match step of `restoreLocalFileLayers` moves, unchanged, into an exported `readLocalVectorFeatures`. A located file is therefore read with the same loader and entry matching that reopening a project uses.
- `useArcgisImportReport.ts` (new hook) holds the report, the repair session and the Locate action. It replaces the `arcgisImportWarnings` / `setArcgisImportWarnings` state; the import calls `arcgisImportReport.show(warnings, session)` once. `ArcgisImportReportDialog.tsx` (new, following `QgisImportReportDialog.tsx`) renders it, with the same `arcgisImportReason.*` strings the old dialog used, so the hosted feature service warnings from #3548 (`service`, `service-unavailable`) read exactly as before. `useProjectFileActions.ts` changes by about 20 lines: it reads the folder layers before the load and hands the session to the report.
- `addLayer` takes an optional third argument, `{ keepName: true }`. With it, a name that matches the file name is not numbered when another layer already has that name. This replaces the earlier `addLayer` + `updateLayer` rename, which wrote twice and left two undo steps per layer.

The Locate step is desktop only, because the browser build cannot read local paths. The browser build leaves `repair.unresolvedLayers` out (their `network-path` warnings stay) and prunes the groups only those layers used.

## Design decisions and known limits

**Path handling**
- *Workspace identity.* Layers are grouped by the full resolved workspace path, never by folder name. `C:\A\Data` and `D:\B\Data` are two entries, and a pick for one never applies to the other. Windows drive paths and UNC paths compare case-insensitively, as NTFS and SMB do. POSIX paths keep their case, so `/Volumes/GIS` and `/Volumes/gis` are different folders. Separators are normalised (`\`, `/` and mixed). Trailing separators are dropped, except the one a root needs (`E:\`, `/`), and `.`/`..` are resolved.
- *Relative and rooted workspaces* resolve the way ArcGIS Pro resolves them. A relative path is relative to the project file. A single leading separator (`\GISData`) means the root of the project's own drive or share. A relative path in a project opened from a share lands on that share, so it is a `network-path` layer, but it can still be located.
- *UNC paths.* Two leading separators of any kind (`\\`, `//`, `\/`, `/\`) mean a share. `..` cannot climb above `\\server\share`, a drive root or the POSIX root. Before, a leading `..` on an absolute path was kept as a literal segment. A GeoTIFF raster whose resolved path lands on a share is now reported as `network-path` instead of being handed to the raster loader, which matches vector layers.
- *Network-share folders are refused as a Locate target.* The picked folder must pass `isAbsoluteLocalPath`, which since the foundation also rejects `//server/share`. Otherwise the report asks for a local or mapped drive and nothing changes. A saved GeoLibre project never reopens layers from a UNC path, so loading them from one would lose them on the next open. A mapped drive letter works.

**Reading only what the user picked**
- The dataset name comes from an untrusted project file and is joined onto the picked folder. `folderSource` therefore rejects any dataset with a `..` segment or a `:` (a drive such as `C:\x` or `C:x`, or an NTFS stream). A POSIX file name containing `:` is not offered either, which is rare and errs on the safe side. Leading and repeated separators and `.` segments collapse, so `/etc/roads` can only mean `etc/roads.shp` inside the picked folder.
- Nothing is searched. Only the expected file names are read, from the one folder the user picked or a subfolder the dataset names. The project file is not changed.
- A file directly inside the picked folder matches exactly, or ignoring case when exactly one entry matches. Windows projects record names as typed, not as stored, so on a case-sensitive disk `Roads.shp` would otherwise miss `roads.shp`. An exact match always wins. With no exact match, two case-insensitive candidates (`roads.shp` and `ROADS.SHP`) give no match rather than a guess. If the folder cannot be listed, the exact name is tried. A dataset in a subfolder (`Sub/Roads.shp`, rare for folder workspaces) must match exactly, because matching each subfolder's case would mean listing folders the user did not pick. The user guide states this.
- Containment is lexical: every path read is the picked folder joined with a relative name that has no `..`, drive or root. Symlinks inside the picked folder are followed, as for any other file the user opens. The folder and its contents are the user's own choice, and refusing links that point elsewhere would break ordinary setups such as a data folder linked from another disk.

**Layer order**
- The repair session keeps the import's bottom-first `layerOrder` and the import-id → store-id map the import built (project layers keep their ids; rasters and hosted or vector-tile services get theirs as they land, and a service that failed is left out). Group contiguity keeps an outermost group and everything nested in it in one block, wherever the user has moved it. So a located layer goes next to the nearest member of its outermost group in the saved order that is on the map: just below the one above it, or else just above the one below it. Using the outermost group rather than the direct one keeps the layer inside its block after the user moves the group; placing it next to a saved member means the next step does not move members across a layer the user added to the group, except where it undoes an arrangement contiguity made while a member was missing (see the next point). With no member of that group on the map, the layer joins any layer the user put in the group, or else goes just below the block of the next imported item above it in the saved order, or else just above the block of the previous one.
- Then one `withoutHistory(() => applyLayerOrder(...))` runs over the import's layers. Each outermost group a layer was located into is refilled, in the slots it holds now, with its members in saved order. This places the located layers among their siblings, and undoes any arrangement contiguity made while a member was missing (for `Outer[Top, Inner[Middle], Bottom]` without `Bottom`, the import leaves `Middle` below `Top`). Each group is refilled separately, so two located groups the user swapped stay swapped. Every other imported layer keeps the place it has now, so a rearrangement the user made after the import outside those groups is kept, and a layer the user added is not jumped over. `applyLayerOrder` also runs `normalizeGroupContiguity`. A rearrangement inside a located layer's outermost group is put back to the saved order; that is the cost of matching a full import.
- Tests import each case twice: once with every file found, and once with some files missing and then located. The final order and groups must match. The cases are a layer below a tiled service, a layer between two hosted feature layers in its group, a group whose only other member is a raster (the earlier review's group-splitting case), a group's last vector below its raster, two missing layers around a grouped raster, a nested group's only layer, an outer group's own bottom layer, each of two siblings in a nested group, an ungrouped layer between a group and another layer, an ungrouped layer above or below a group whose nested member moved, grouped and ungrouped layers located together, and two workspaces located last first. Regression tests cover a group the user moved before a layer was located into it (saved `X, G[J[B], H[A]], Y` with `B` missing; `G` moved above `X`), a layer the user added inside the group between saved members, and a group holding only a layer the user added. A seeded randomised test (100 projects, about 0.1 s) generates nested groups with rasters, hosted feature layers and two workspaces, leaves some files missing, moves whole blocks at random, locates the workspaces in random order, and after each Locate compares the blocks with an import that found the same files, with the user's block moves kept. It fails on the previous placement (split groups) and on a single shared saved-order refill (swapped groups put back). 3,000 seeds passed during development. Separate tests cover a rearrangement outside the group being kept and a layer the user added.
- A located layer keeps its import id unless a layer added after the import already holds it. It then gets `<id>-2`, and the session maps the import id to it.
- Each located layer is added with one `addLayer`, a history-producing store action, because locating data is a user action. Normal history coalescing applies, so a Locate that adds several layers at once usually forms one undo entry. The reorder runs through `withoutHistory` and adds nothing of its own.
- Neighbours are found in two linear passes over the saved order (one from the top for the item above, one from the bottom for the item below), using a map of the ids on the map that is updated as layers are added. Finding a slot next to a neighbour or a block's edge scans the store's layers once per located layer, and the reorder builds each located group's saved order in one pass. Matching file names indexes the folder listing once per Locate (an exact-name set and a lower-case map that records ambiguous names) and matches each saved file name once, however many layers read it.

**Project switches**
- The import itself uses the foundation's `ProjectImportSession`. The folder reads happen between the file read and `replaceProject`, and the existing `session.superseded()` check right after them stops the import if another project opened meanwhile. `confirmDiscardAttributeDrafts` is still asked after those reads, right before the load.
- The report belongs to the project the import loaded and records its `projectLoadCount`. When another project replaces it (open or new project), the report closes, even while no Locate is running. A collaboration snapshot refreshing the same project bumps only `projectGeneration`, so the report stays open. A Locate checks the count and its own session after the folder picker, after the folder listing and after the reads. If either changed, the Locate stops at that point: a switch while the picker is up lists nothing, a switch during the listing reads no file, a switch during the reads adds nothing, and an error from the stopped Locate is not shown.
- One Locate at a time. A ref, not only render state, guards this, so a fast double click cannot open two pickers. Committed layers leave the session, so a second Locate cannot add them twice.

**No silent loss**
- Every folder-backed layer that can be located gets a named import warning when it fails to load: `network-path` for a share, `data-not-found` for a missing or unreadable file. Container-backed sources are not offered for Locate and behave as on `main`. A file geodatabase layer in a local workspace gets its named `file-geodatabase` import warning, whether or not the `.gdb` exists; one on a network share gets `network-path`, because the share check comes first. A missing GeoPackage used as the workspace is loaded as a record and then dropped by the reopen restore, whose notification gives a count and path rather than a named import warning.
- A Locate reports how many layers loaded and how many of that folder's layers still could not be loaded. If none of the expected files could be loaded, it says so ("Nothing was changed"). The wording covers both a missing file and one that exists but fails to read (for example a shapefile without its `.dbf`), because the shared loader does not distinguish them. When all warnings are cleared, the report says "All layers listed for repair were loaded." It does not claim more, because a missing GeoPackage workspace is reported by the restore notification instead (see above).

**Scope**
- Only single files inside a folder workspace are offered. A layer whose workspace is itself a container (a file geodatabase, or a GeoPackage named as the workspace) is not, because its data is not a file in a folder (a separate follow-up on #3553 covers file geodatabases). A `.gpkg` named as the dataset of a folder workspace is a file in a folder, so it is offered.
- `.geolibre.json` projects are unaffected. `restoreLocalFileLayers` calls the extracted `readLocalVectorFeatures`, whose body is the code that was inline: the same `loadDroppedVectorPaths` options, the same entry/name/first-entry matching and warning, and the same `null` → drop path.
